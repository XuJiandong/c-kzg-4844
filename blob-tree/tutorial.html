BLOB TREE · RUST · EIP-4844 · PROOF OF CONCEPT

Two levels of blobs.
One membership proof.

Commit to as many as 16,777,216 elements in a tree with just two levels. Whether you query one element or many, the proof reduces to one KZG verification call.

01 / FROM ELEMENTS TO THE PUBLIC ROOT

Every position has a two-level path.

Split an element's zero-based index i into row=⌊i4096⌋ and column=imod4096. Each bottom-level blob stores element hashes. The top-level blob stores hashes of child commitments. Both hashes are reduced modulo the BLS12-381 scalar field modulus r.

Worked example: index 4103=1×4096+7 belongs to child 1, slot 7. Its element hash is committed by C1, and the hash of C1 occupies top-level slot 1.

The root is constructed from the bottom up. Lines show dependencies; the diagram does not draw all 4096 slots to scale.

A blob stores evaluations, not coefficients. Its 4096 slots hold polynomial values at fixed points. Slot s corresponds to ωbitreverse12(s), where ω = γ^((r − 1) / 4096) mod r. Here, γ (gamma) denotes the multiplicative generator of the BLS12-381 scalar field selected by the Ethereum specification; using this fixed generator keeps the evaluation domain consistent with c-kzg. The Rust implementation uses FFTs to convert representations consistently with c-kzg.
02 / QUERIES SHARE CHILD COMMITMENTS

Share child commitments, then combine the openings.

A proof includes an 8-byte query count and an 8-byte index per queried element, then one commitment for each queried child, followed by two points: the aggregate quotient commitment D and the opening witness W. Each point occupies 48 bytes.

For queries [0, 7, 4096, 4097], child 0 supplies columns 0 and 7, while child 1 supplies columns 0 and 1. The four queries share two child commitments.

The complete reduction, step by step

The reduction first commits to an aggregate quotient polynomial and then checks its relation to the claimed openings at a transcript-derived point. All five steps are shown below. Here, statement 0 is the top level, and statements 1 through m are the queried children in ascending child-index order.

Where Shplonk is used: steps 2–4 perform the Shplonk-style reduction: aggregate the quotient polynomials, commit to the aggregate before deriving the checking point, then reduce all claimed openings to the single claim g(z) = y. Step 1 binds the public statement to the transcript; step 5 completes the proof with a standard single-point KZG opening and verification. This implementation defines its own transcript and wire format; it does not claim interoperability with other Shplonk implementations.
STEP 1 / FIX THE STATEMENT

Bind everything the proof claims.

T=Encode(protocol domain, root, queries,values, child commitments)

The root contains both the commitment and vector length. The top-level opening claims child-commitment hashes; each child opening claims element hashes. Queries and child commitments use their canonical order. Encode includes the counts and lengths specified in the design document.

STEP 2 / SHPLONK · DERIVE ρ

Combine the quotient polynomials.

ρ=hash_field(“rho”,[T]) qi(X)=fi(X)−Ii(X)Zi(X) Q(X)=∑i=0mρiqi(X)

Ii interpolates the claimed point-value pairs, and Zi vanishes at their evaluation points. The division has no remainder when the opening claims are correct. The nonzero coefficient ρ is derived from the complete transcript.

STEP 3 / SHPLONK · COMMIT TO THE QUOTIENT

Fix D before deriving the checking point.

D=Commit(Q) z=hash_field(“z”,[T,D])

D is the first of the two additional proof points. Deriving z from both T and D binds the checking point to the quotient commitment. Each hash_field call uses domain-separated, length-prefixed SHA-256 followed by reduction modulo r.

STEP 4 / SHPLONK · DERIVE A SINGLE OPENING CLAIM

Reconstruct the combined commitment.

ai=ρiZi(z) g(X)=∑i=0maifi(X)−Q(X) Cg=∑i=0maiCi−D y=∑i=0maiIi(z)

The remaining claim is g(z)=y. The verifier derives every weight, the commitment Cg, and y from the public statement and D. No additional evaluations need to be transmitted.

STEP 5 / KZG · OPEN AND VERIFY

Check one equation with two pairing terms.

W=KZG opening witness forg(z)=y e(Cg−y·G1,G2)=e(W,[τ]G2−z·G2)

W is the second additional 48-byte point. The verifier calls c-kzg's verify_kzg_proof once. The pairing equation uses two Miller loops and one final exponentiation. Beyond the count, indices, and child commitments, the proof always contains exactly 96 bytes.

The order is T → ρ → D → z → W. This static tutorial explains the structure and proof size; run the Rust example to perform actual cryptographic computations.

03 / SECURITY DEPENDS ON THE COMPLETE RELATION

Connect each element all the way to the root.

Verify both levels

The child opening binds the element to its child commitment. The top-level opening binds that commitment's hash to the root. Both are needed to establish membership in this tree.

Preserve the transcript order

The challenge ρ binds the complete statement; z also binds D. Letting the prover choose D after seeing z would let it tailor a false relation to that single checking point.

Hash before reducing

Directly reducing raw integers would identify x and x+r. Instead, SHA-256 hashes domain-separated, length-prefixed byte strings before the digest is reduced to a field element.

Authenticate the length

The trusted root is the complete pair (R, n). Out-of-range and padding positions are not members. Queries must be strictly increasing, unique, and less than n.

Degenerate challenges and special curve points

If ρ is zero or z equals any queried evaluation point at either tree level, retry its hash with a big-endian u64 nonce starting at 1. Prover and verifier select the first valid candidate independently, so no nonce is sent. Retrying z keeps the transcript and quotient commitment fixed. Counter exhaustion returns an error. All external G1 points undergo canonical-encoding and subgroup checks. The point at infinity is permitted because a zero polynomial has a valid zero commitment. Applications must accept only a verification result of Ok(true).

Assumptions and limits

This proof of concept has not undergone an independent cryptographic audit. It depends on a trusted root, the Ethereum trusted setup, KZG binding, and SHA-256 security assumptions. It provides neither hiding nor zero knowledge. Negative tests help detect implementation errors but cannot replace a cryptographic audit. Large public statements also require application-level resource limits.

04 / FROM THE DIAGRAM TO THE CODE

Run a proof across both levels.

From the repository root:

cargo test --manifest-path blob-tree/Cargo.toml --locked
cargo run --manifest-path blob-tree/Cargo.toml --example basic --locked

The example uses the public API as follows, with enough values to include every queried index:

let tree = Tree::new(&values)?;
// Tree construction and verification sort values by big-endian byte order.
// Duplicate values are rejected. Indices refer to positions in the sorted tree.
// Check proof.indices if your application requires specific positions.
let (values, proof) = tree.prove(&[0, 7, 4096, 4097])?;
assert!(verify(tree.root(), &values, &proof)?);
// Four indices, two children: 8 + 4 × 8 + 2 × 48 + 96 = 232 bytes
